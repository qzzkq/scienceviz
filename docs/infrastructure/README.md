# Запуск MPI на машинах команды

Для проверки связи между машинами запустите `mpi_hello` на двух узлах,
затем измерьте время пересылки данных с помощью `mpi_pingpong`.

## Подготовка каждого узла

1. Подключить машины к одной проводной сети. Проверить согласованные адреса
   и уникальные имена узлов. Реальные IP и учётные данные хранить локально.
2. На каждой машине установить C++17-компилятор, CMake, Python с venv и одну
   согласованную версию MPI. Для первого эксперимента можно повторить
   `build-mpi-env` из [основной инструкции](../mpi.md) на каждом узле.
3. Собрать один и тот же коммит проекта на каждом узле. Использовать одинаковый
   абсолютный путь до checkout и MPI-окружения либо согласовать launcher со
   своими путями. Коммит сверять командой `git rev-parse HEAD`.
4. Включить SSH-сервер на вычислительных узлах. С запускающего узла проверить
   вход под своей учётной записью. При первом подключении сверить ключ узла;
   существующие SSH-ключи и настройки не перезаписывать.
5. Проверить выполнение без интерактивного ввода:
   `ssh -o BatchMode=yes USER@NODE 'hostname; command -v c++'`.
   Установка ключа на удалённой машине выполняется её владельцем или с его
   разрешения. Пароли и закрытые ключи не помещать в репозиторий.
6. Проверить разрешение имён и связность между узлами. Для MPICH/Hydra SSH
   используется для старта процессов; обмен MPI также требует доступных
   TCP-портов между узлами. Требования зависят от транспортной библиотеки.
   Согласовать правила для выбранной MPI с администратором сети; открытого
   SSH-порта недостаточно. Брандмауэр целиком не отключать.
7. Запустить `scripts/collect_hardware.py --node ИМЯ_УЗЛА` на каждом узле
   и заполнить таблицу оборудования. Отдельно записать тип и скорость
   фактического проводного соединения.

## Проверка двух узлов (MPICH/Hydra)

Создать локальный `out/hosts-2.txt`, по одному узлу на строку:

```text
node-a:1
node-b:1
```

Имена заменить согласованными SSH-host aliases/IP. На удалённых узлах должны
быть доступны исполняемый файл и MPI-библиотеки. Пример из корня checkout:

```bash
build-mpi-env/bin/mpiexec -f out/hosts-2.txt -n 2 \
  "$PWD/build-mpi/mpi_hello" --min-hosts 2
build-mpi-env/bin/mpiexec -f out/hosts-2.txt -n 2 \
  "$PWD/build-mpi/mpi_pingpong" > out/pingpong-two-nodes.csv
```

Критерий: два разных имени хостов и `unique_hosts=2 ... PASS`. Уникальные имена
нужны для этой проверки; дополнительно сверять их с реальным оборудованием.
Два процесса на одном ноутбуке этот критерий не выполняют.

Пинг-понг измеряет половину времени кругового обмена и эффективную скорость
полезной нагрузки на размерах от 1 байта до 1 MiB. Есть прогрев и проверка
содержимого. Эти значения описывают выбранный MPI-транспорт, а не только
физическую сеть. Для сравнения сохранить локальный результат на том же наборе
размеров и несколько повторов на двух машинах.

## Три узла

Добавить третий узел в `out/hosts-3.txt`, по одному процессу на узел:

```bash
build-mpi-env/bin/mpiexec -f out/hosts-3.txt -n 3 \
  "$PWD/build-mpi/mpi_hello" --min-hosts 3
build-mpi-env/bin/mpiexec -f out/hosts-3.txt -n 3 \
  "$PWD/build-mpi/svmpi_tests"
build-mpi-env/bin/mpiexec -f out/hosts-3.txt -n 3 \
  "$PWD/build-mpi/mpi_diffusion" --nx 17 --ny 13 --nz 19 --halo 2 --steps 20
```

Критерии: три разных физических машины, тесты без ошибок, `verified: true` у
диффузии, сохранённые параметры сети, версии MPI, коммит и логи запусков.
На кластере команды запуска и размещение процессов задаёт его scheduler;
приведённый SSH/hostfile пример не заменяет инструкции кластера.

## Текущий незавершённый объём

- Контакт кластера и отправка письма.
- Характеристики двух остальных узлов команды.
- SSH, проводная сеть, запуск на двух и трёх физических машинах.
- Реальные сетевые измерения и сравнение повторов.

Подготовленные инструкции и локальные логи не закрывают эти пункты.
